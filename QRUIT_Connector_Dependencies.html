1. How QRUIT connectors work

A connector (called a channel in the code) is a small Python class that talks to one external service. Every connector implements the same five functions, so the rest of QRUIT does not care whether a CV came from Gmail, SharePoint or a folder on disk:

Python functionWhat it doesUsed by
auth_status() / status_detail()Reports ready, needs_auth (no token yet or a permission missing) or error (credentials not configured) with a human sentence.Channels page, Inbox storage tabs
pull(query=, limit=, folder=)Lists candidate items on the service — messages with attachments, files in a folder — applying the service's own search/filter syntax. Returns InboundItem records (name, sender, subject, size, received time, opaque reference).Inbox → Pull now / Sync All / Process folder; the job agent; the chat tool pull_channel
fetch(item_id, dest_dir)Downloads one item to disk so it can be converted to DOCX/text, classified (JD / CV / command) and de-duplicated.Ingestion pipeline
browse(path)Storage services only: one level of the folder tree with JD/CV detection counts, so a user can pick a folder to process.Inbox → Storage tab
send(OutboundMessage)Sends a rendered message (subject, body, optional attachments) and returns a receipt with the provider's message id.Delivery service — only after a human approval token exists
Two rules that shape every dependency below Pull on request. QRUIT never keeps a mailbox subscription, folder watcher or webhook open; it queries a service when a person or the job agent asks. Send after approval. Every outbound message waits for a human to approve a checkpoint in the console. Consequently the connectors need read scopes plus a send scope, and nothing that grants write access to files, labels or settings.

The OAuth 2.0 flow both Google and Microsoft connectors use

Gmail, Google Drive, Outlook and SharePoint all authenticate the same way — authorization code with PKCE, performed once by a person, after which a refresh token lets QRUIT work unattended. The code lives in backend/app/channels/oauth_base.py.

  1. authorize_url() builds the provider's consent URL with the client ID, the requested scopes, a random state and a PKCE code_challenge; the console opens it in a popup when a user clicks Connect.
  2. The user signs in as the recruiting account and accepts the scopes. The provider redirects to {QRUIT host}/api/oauth/callback?code=…&state=…. This redirect URI must be registered with the provider exactly (see each service).
  3. handle_callback() exchanges the code (plus the PKCE verifier and client secret) for an access token and a refresh token, asks the provider who the account is, and stores the token blob encrypted.
  4. access_token() refreshes automatically two minutes before expiry using the refresh token — no human involvement after step 2.
  5. auth_status() compares the scopes actually granted with the scopes the connector requires; if a send scope is missing it reports needs_auth and the console shows reconnect to grant send permission.
What that means for provisioningFor each provider we need: (1) an application registration that yields a client ID + client secret, (2) the redirect URI(s) registered on that application, (3) the scopes/permissions approved, (4) an account to sign in with that can see the mail and folders in question. Everything else is derived at runtime.

3. Gmail

What the connector does

GmailChannel in backend/app/channels/google.py. pull() runs a Gmail search (default newer_than:90d has:attachment, or any query the user types, e.g. from:agency.com subject:CV label:QRUIT), reads each matching message, and lists every attachment; when a query is given it also returns plain-text bodies (pasted JDs, reply commands such as PROCEED). fetch() downloads the attachment bytes. send() builds an RFC-2822 MIME message (with PDF attachments for reports) and sends it from the connected mailbox.

7. E-mail alerts to registered addresses

What QRUIT sends, to whom, through which connector

QRUIT does not run a separate mail server. Every alert is rendered from a template in backend/app/services/templates.py and handed to DeliveryService.send(), which picks the first ready connector that can send to the recipient: for an e-mail address that is the connected Gmail or Outlook mailbox (§3, §5); for a phone number it is WhatsApp (§8). Until a mailbox is connected (or while QRUIT_EMAIL_MOCK=true) messages are written to backend/data/outbox/ instead of being sent, so the pipeline can be exercised safely.

status_updateClient contactOn request from the console, the chat (send_status_update) or the agent; also the SLA reminder when an approval has been waiting longer than sla_hoursGuided mode: waits for approval

candidate_ack, interview_invite, interview_reminder, interview_nudgeCandidate — e-mail extracted from the CV (or the sender address of the mail that carried it)After standardisation; after the shortlist approval; before a booked slot; when an invitation is unansweredGuided mode: each waits for approval

8. WhatsApp Business (Meta Cloud API)

What the connector does

WhatsAppChannel in backend/app/channels/whatsapp.py with an HttpTransport: send() posts a text or template message to https://graph.facebook.com/v20.0/{phone-number-id}/messages with a bearer token and returns the wamid. Used for interview invitations, reminders and the client digest.

Inbound is different from the other connectorsThe Cloud API has no endpoint to list received messages; Meta delivers them only to a webhook. Because QRUIT is pull-only by design, WhatsApp is send-only when live and pull() returns nothing. Receiving CVs or reply commands over WhatsApp requires the webhook items WA-6/WA-7 and a decision (§12 C3).
